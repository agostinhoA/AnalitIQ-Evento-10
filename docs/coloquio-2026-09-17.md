## Definición del rango y de deuda

El documento previo tiene `cuotas.fecha_vencimiento` y estados `Adeuda`/`Pagada`, pero el evento anterior no define un rango. El proceso 2.1.3.2 de otro evento identifica cuotas adeudadas por su estado sin verificar vencimiento. Esto no resuelve por sí solo el nuevo criterio del coloquio.

Se consultaron esas precisiones antes de implementar el filtro. La respuesta del usuario confirmó vencimiento, sólo cuotas impagas vencidas incluyendo las que vencen hoy, y ambas fechas obligatorias. Se comunicó que los dos extremos se tomarían incluidos, criterio implementado y visible en el formulario.

Una cuota se muestra si cumple simultáneamente:

```text
tratamientos.activo = 'SI'
estados_cuotas.tipo_estado = 'Adeuda'
Desde <= cuotas.fecha_vencimiento <= Hasta
cuotas.fecha_vencimiento <= hoy
```

`hoy` se determina una sola vez por informe en `America/Argentina/Buenos_Aires`, no desde la fecha del navegador ni la zona horaria del MySQL de destino. La fecha de corte aparece en pantalla. La aplicación no permite que un parámetro HTTP cambie esa fecha; las pruebas JDBC inyectan un Clock fijo para comprobar hoy, mañana y el cambio de día.

El rango se valida en Java: ambas fechas obligatorias, fechas de calendario reales, Desde no posterior a Hasta, formato ISO de los controles HTML y dominio DATE de MySQL (años 1000–9999). Un rango de un solo día es válido; un rango futuro es válido pero no hace aparecer cuotas aún no vencidas. Todos los filtros se envían como parámetros JDBC, incluidos ambos extremos y hoy.

La búsqueda conserva el rango en `BusquedaSesion`. La selección ignora fechas o tipos enviados adicionalmente por el cliente. Aplicar otro rango crea un identificador de flujo nuevo, conserva al paciente validado y no modifica informes anteriores de otras pestañas. Un filtro inválido devuelve HTTP 400, conserva el informe anterior y lo informa explícitamente.

## Inspección de datos y pagos parciales

En la base local anterior a este cambio hay tres pacientes con un tratamiento activo cada uno, sin tipos activos repetidos ni pacientes con más de tres. El catálogo sólo tiene `Adeuda` y `Pagada`; no se encontró código para registrar pagos parciales. Las cuotas relacionadas con pagos existentes están en estado Pagada. El pago 503 cubre dos cuotas completas de 30.000 y el pago 504 una de 20.000.

`cuotas_x_pagos` sólo contiene las claves de cuota y pago: no guarda importe imputado. Por ello una validación general de pagos parciales históricos no puede inventar distribuciones por cuota. No se modifica este vínculo ni el evento de registro. Si aparecen datos incompatibles, deben revisarse en un proceso de corrección aparte, no descontarse automáticamente de la deuda presentada.
